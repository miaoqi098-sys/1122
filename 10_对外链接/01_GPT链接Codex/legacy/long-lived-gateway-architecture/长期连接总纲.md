# GPT→Codex 长期连接总纲

## 一、正式主链

```text
ChatGPT 对话
  ↓
GPT-Codex 自定义 MCP 应用
  ↓
长期认证（OAuth + refresh token / offline access）
  ↓
安全远程通道
  ↓
本机常驻 GPT-Codex Gateway
  ↓
Codex App Server
  ↓
Codex Thread
  ↓
本机文件 / CLI / Git / API / 浏览器工具 / 其他受控执行器
```

## 二、为什么不用 GitHub / AACC 做主链

长期执行链必须满足：低延迟、跨对话、低授权摩擦、可持续会话、实时事件返回。因此 GitHub Issue 轮询不承担实时控制面；AACC 也不是依赖项。

GitHub在本工程中的角色仅为：
- 源码仓库；
- 配置版本；
- 代码审计；
- 可选备份和发布。

## 三、跨对话定义

“任意 GPT 对话”指：

- 同一个已授权 ChatGPT 账户或工作空间；
- 已启用本工程发布的 GPT-Codex 应用；
- 当前对话具备该应用的工具访问资格。

连接状态不存放在聊天上下文，而存放在长期认证和 Gateway Runtime 中。因此新对话不需要恢复旧聊天才能使用 Codex。

## 四、长期连接定义

首次安装/授权后：

1. ChatGPT 侧保存应用连接关系；
2. OAuth 提供 refresh token，并支持离线续期；
3. Gateway 保持常驻服务；
4. Codex App Server 由 Gateway 管理并自动恢复；
5. 每次 GPT 请求直接创建/复用 Codex thread，不重复走 GitHub Issue；
6. 授权过期时优先自动刷新，仅在刷新失效或平台要求重新认证时才需要人工动作。

## 五、线程策略

- `conversation_scoped`：单个 GPT 对话可绑定一个 Codex thread，保持连续施工上下文。
- `project_scoped`：同一工程可维护长期 Codex project thread/index，支持新对话恢复项目上下文。
- `ephemeral`：一次性小任务仍可创建临时 thread，但不是主模式。

默认：`project_scoped + conversation child thread`。

## 六、执行权限模型

默认高权限：`HIGH_AUTHORITY`。

Gateway 不人为增加大量审批点。对可逆的本机工程操作默认自动执行；对于不可逆且高损失的极少数动作才需要硬确认。

Codex 的权限由三层共同决定：

```text
ChatGPT App权限
    ↓
Gateway权限策略
    ↓
操作系统/连接器本身权限
```

不得通过关闭身份认证来实现“少授权”；正确方式是一次长期认证 + 自动刷新 + 高权限策略。

## 七、可用性目标

长期运行目标：

- Gateway 随系统登录自动启动；
- App Server 异常自动重启；
- 连接中断自动重连；
- OAuth 自动刷新；
- 任务有 idempotency key，避免网络恢复后重复执行；
- 新 GPT 对话无需 GitHub、无需 AACC、无需重复输入密钥；
- 执行状态可查询：ONLINE / DEGRADED / AUTH_REQUIRED / CODEX_UNAVAILABLE / OFFLINE。

## 八、事实边界

`架构文件存在` 不等于 `长期连接已上线`。

真正验收必须至少证明：

1. Gateway 本机常驻成功；
2. Codex App Server 可持续双向通信；
3. MCP 工具可从 ChatGPT 调用；
4. 首次授权后可刷新续期；
5. 关闭当前聊天，打开新聊天仍能执行一次真实 Codex 操作；
6. 不经过 GitHub Issue；
7. 不经过 AACC；
8. 重启电脑后可恢复。
