# 证据与整改申诉框架

## 目标
统一风险事件从“发生什么”到“需要什么证据、如何整改、如何形成申诉/回复材料”的框架。Agent-12只组织事实与论证结构，不伪造文件、不保证申诉成功，也不直接提交。

## 证据分层
1. `platform_notice`：平台通知、Case、Account Health、审核要求；
2. `product_fact`：产品规格、材质、成分、标签、包装、说明书；
3. `qualification_document`：检测、认证、发票、授权、SDS等文件；
4. `listing_fact`：标题、图片、A+、属性、前台展示；
5. `operation_record`：采购、质检、供应商、整改、培训、流程记录；
6. `customer_evidence`：评论/VOC/安全反馈；
7. `policy_rule`：适用规则及版本；
8. `execution_evidence`：已完成修改/移除/补充文件的真实回执。

## 证据质量
每份证据记录：source、issued_at、valid_until、scope、document_id/ref、issuer、consistency_status、freshness、confidence。文件名称存在不等于内容满足要求。

## 根因框架
根因必须解释“为什么发生”，而不是复述违规通知。可从：产品/供应商、内容、资料、流程、权限、培训、数据同步、系统错误等层面分析，并绑定证据。

## 整改结构
- Immediate containment：立即控制风险；
- Corrective action：纠正已发生问题；
- Preventive action：防止复发；
- Owner / due date；
- verification_method；
- execution_evidence_ref。

## 申诉/回复材料结构
1. 问题与通知引用；
2. 已核实事实；
3. 根因；
4. 已完成纠正措施；
5. 预防措施；
6. 支撑文件清单；
7. 尚缺资料/不确定项；
8. 请求平台复核的具体事项。

## 禁止事项
- 不编造发票、授权、检测或认证；
- 不把计划中的整改写成“已完成”；
- 不承诺平台一定恢复；
- 不隐藏与申诉不利但关键的事实；
- 不使用未经核实的政策条文作为核心论据。
