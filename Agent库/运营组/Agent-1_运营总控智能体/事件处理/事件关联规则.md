# 事件关联规则

## 1. 目的
当事件不能去重或合并，但存在明确业务关系时，通过关联保持上下文连续性。事件关系必须显式表达方向，不能只依赖 source_event_id / target_event_id 的排列顺序猜测语义。

## 2. 关联类型与方向
### 对称关系
- `same_scope`：同一业务对象；
- `conflicting_evidence`：双方证据互相冲突；
- 其他经定义为双向等价的关系。

对称关系应记录：`direction=symmetric`，无需通过创建两条镜像关系表达同一个事实。

### 有向关系
- `parent_child_scope`：父层对象 → 子层对象；
- `temporal`：较早事件 → 后续事件；
- `causal_candidate`：候选原因 → 候选结果；
- `dependency`：依赖方 → 被依赖前置事件；
- `follow_up`：原事件 → 后续验证/结果事件；
- `same_strategy_chain` / `same_decision_item` 若仅表达共同归属，可按实现选择对称；若表达来源链，则必须声明方向。

有向关系应记录：`direction=directed`，并在适用时保留 `inverse_relation`。

## 3. 关联记录
每条关系至少保留：
- source_event_id；
- target_event_id；
- relation_type；
- direction；
- inverse_relation（适用时）；
- relation_status；
- reason；
- evidence_refs；
- confidence（适用时）；
- created_at。

`relation_status` 建议：
- `candidate`：候选关系，尚未证实；
- `confirmed`：证据足以支持该关系；
- `rejected`：后续证据否定该关系；
- `unknown`：暂无法判断。

## 4. 因果谨慎
`causal_candidate` 默认 relation_status=candidate，只表示待验证因果假设。不能因为两个事件先后发生就直接标记 confirmed causal relation。

## 5. dependency 语义
统一定义：

`source_event_id dependency target_event_id`

表示 source 事件的处理依赖 target 事件先满足前置条件。

若系统需要反向查询，应使用 inverse_relation（例如 `blocks`），不得在不同模块中反向解释同一 dependency 字段。

## 6. StrategyChain关系
事件若与运行中策略有关，应保留 strategy_chain_id 或可追溯到相关 decision/task；事件本身不直接修改 StrategyChain 状态。

## 7. 冲突关系
不同来源给出相反事实时，建立 `conflicting_evidence` 对称关系并交 S03/后续证据判断，不得通过合并删除一方。

## 8. 禁止
- 只因同一 ASIN 就认为事件因果相关；
- 把相关性直接当因果；
- dependency 在不同模块中使用相反方向语义；
- 关联后删除独立 event_id；
- 用 related_events 数组替代真正需要的冲突处理；
- 对同一对称关系重复创建无意义的 A→B、B→A 镜像记录。
