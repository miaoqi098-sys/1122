# 事件关闭与解决证据

## 1. 定位
本规则定义事件从 `open/monitoring` 进入 `resolved/closed` 时必须具备的正向证据，避免仅因 Task 完成、时间经过或上游标签变化就误判事件已解决。

## 2. resolved 的最低证据
事件进入 `resolved` 至少应保留：
- `resolution_basis`；
- `resolution_evidence_refs`；
- `resolution_source`；
- `resolution_confidence`；
- `resolved_at`；
- 若由执行动作产生结果，保留 `validation_refs` 或可追溯到 ExecutionResult/ValidationResult 的引用。

## 3. resolution_basis
允许的主要类型：
- `action_effect_verified`：执行动作后的效果已被验证；
- `natural_recovery`：问题自然恢复，与执行动作不能直接建立因果；
- `disproved`：事件核心事实被证伪；
- `canonical_event_takeover`：已由其他 canonical event 承接且无需独立追踪；
- `window_expired`：风险/机会窗口结束且无继续处理价值；
- `other`：其他可解释且有证据的解决原因。

## 4. Task、Decision 与 Event 的边界
- Task `completed` 只说明任务执行完成，不自动代表 Event `resolved`；
- FinalDecision `completed` 也不自动代表 Event `resolved`；
- S08/ValidationResult 若确认目标效果达成，可作为 `action_effect_verified` 的关键证据；
- 若动作失败但问题自然恢复，应记录 `natural_recovery`，不得伪造为动作成功；
- 若事件被证伪，应保留原证据和证伪依据，而不是删除事件。

## 5. closed 条件
`resolved` 后完成必要观察，且没有新的有效触发时方可进入 `closed`。关闭必须记录：
- `closed_at`；
- `close_reason`；
- 必要的观察/验证引用。

对于 `canonical_event_takeover` 或明确无继续价值的事件，可以按规则直接关闭，但必须保留承接事件引用。

## 6. reopen
关闭后的事件只有出现新发生事实或新证据时才能重新进入处理链。`reopen` 是状态转换动作，不是长期 event_status。

## 7. 禁止
- Task completed → Event resolved 的机械映射；
- 没有 resolution evidence 就关闭高影响事件；
- 动作失败但问题自然恢复时宣称动作成功；
- 关闭事件后删除历史证据；
- opportunity window 结束后仍无限保持 open 而不说明原因。
