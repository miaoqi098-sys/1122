# 事件合并规则

## 1. 目的
把多个高度相关事件组织成一个可管理事件组，减少重复决策，同时避免粗暴丢失来源、差异和时间演化。

## 2. 可合并条件
通常需要同时满足：
- scope相同或存在明确父子scope；
- event_type相同或属于同一经营问题；
- 时间窗口高度重叠；
- 合并后不会掩盖不同风险/资格；
- 对DecisionItem的核心问题定义一致。

## 3. 不应合并
以下情况应保持独立并建立关联：
- 不同goal_layer产生不同决策冲突；
- 一个是合规风险、另一个只是增长机会；
- 不同scope需要不同动作；
- 证据方向明显冲突；
- 一个事件已resolved，另一个是新周期重新发生；
- 合并会导致严重度、deadline或责任方被模糊。

## 4. 合并结果
建议形成：
- canonical_event_id；
- merged_event_ids[]；
- source_refs[]；
- evidence_refs[]；
- first_seen_at / last_seen_at；
- merged_summary；
- preserved_differences[]；
- current_severity；
- scope；
- merge_reason。

原event_id不得删除。

## 5. severity合并
不得简单取最大值或平均值。应根据最新证据、影响范围和当前状态重新判断，并记录为什么当前severity成立。

## 6. 与DecisionItemBuilder
一个事件组可以形成一个DecisionItem，也可以在保留同一canonical_event_group引用的前提下拆成多个DecisionItem。是否拆分取决于是否存在不同问题/目标/动作边界。

## 7. 禁止
- 为了减少数量把所有同ASIN事件合成一个；
- 合并后丢失来源agent和evidence_refs；
- 通过合并隐藏冲突证据；
- 合并后重复生成与原事件完全相同的DecisionItem。
