# 事件生命周期

## 1. 状态
标准事件生命周期建议：

```text
open
→ updated
→ resolved
→ closed
→ reopened
```

辅助归并状态：
- `suppressed_duplicate`
- `merged`

## 2. open
事件首次确认有效并需要继续处理/观察。

## 3. updated
同一事件出现新证据、scope变化、severity变化、deadline变化或状态变化，但仍属于同一事件。

必须保留变化原因和新证据，不覆盖历史快照。

## 4. resolved
当前触发问题已经消除或得到充分处理，但仍处于观察/验证窗口。

resolved不等于历史删除，也不表示所有相关Task已经完成。

## 5. closed
满足关闭条件：
- 问题已解决并完成必要观察；或
- 事件被证伪；或
- 已明确由其他canonical事件承接且无需独立追踪；或
- 机会/风险窗口已结束且无后续价值。

关闭必须记录close_reason与closed_at。

## 6. reopened
已closed事件只有出现新证据或新发生事实时才能重开。

必须记录：
- reopen_reason；
- new_evidence_refs；
- reopened_at；
- 是否属于原事件延续还是新周期事件。

如果本质是新周期独立发生，应创建new_event并建立follow_up关系，而不是无限reopened同一个event_id。

## 7. duplicate/merged
- suppressed_duplicate：保留原event_id和source refs，指向canonical_event_id；
- merged：保留原事件并记录merged_into。

## 8. 防重复触发
resolved/closed/duplicate/merged事件不得无新证据重复生成相同DecisionItem。

## 9. 禁止
- 通过关闭事件删除历史；
- Task completed就自动推断Event resolved；
- closed事件无新事实周期性重开；
- 用同一event_id承载无限多个完全不同的新周期问题。
