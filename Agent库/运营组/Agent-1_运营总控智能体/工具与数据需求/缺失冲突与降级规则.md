# 缺失、冲突与降级规则

## 1. 目标

本文件规定数据/工具条件不完整时 Agent-1 如何继续安全判断，避免两类错误：
1. 缺数据就完全停摆；
2. 缺数据却自行补值并假装确定。

## 2. 数据异常类型

- no_data：目标事实不存在；
- stale_data：存在但已不满足新鲜度；
- incomplete_result：关键字段不完整；
- source_conflict：多个来源的同一事实无法解释地冲突；
- scope_mismatch：来源Scope与DecisionItem不匹配；
- window_mismatch：数据窗口不可直接比较；
- quality_below_minimum：证据质量低于当前动作要求；
- attribution_delay：结果尚处归因/结算延迟期；
- permission_denied：无法取得数据或能力；
- tool_error：工具层失败；
- unsupported：当前来源或工具不支持请求。

## 3. required数据缺失

先判断required是“资格型”还是“质量型”。

### 资格型required
缺失会决定能不能做，例如可售资格、合规状态、库存可售事实、关键审批。

默认：
`request_refresh / request_specialist / hold_for_review / block_option`

不得用低质量历史值替代后直接执行高影响动作。

### 质量型required
缺失会显著降低判断可靠性但不一定决定合法性。

可选：
- 请求补数；
- 缩小动作范围；
- 改为低风险测试；
- 降低decision_confidence；
- 延长观察；
- hold。

## 4. preferred数据缺失

原则上不阻塞全部决策。

应评估：
- 缺失是否会使两个方案无法区分；
- 当前动作是否可逆；
- 是否有可信fallback；
- 是否可通过更窄Scope/更小动作降低风险。

## 5. 来源冲突处理

顺序：
1. 对齐对象ID和Scope；
2. 对齐时间点/窗口；
3. 确认raw fact还是derived metric；
4. 对齐公式/口径版本；
5. 检查数据延迟与缓存；
6. 检查专业Agent是否基于旧快照；
7. 根据事实类型选择更权威来源；
8. 仍无法解释则保留冲突，不强行平均。

无法消解且会影响方案资格时：进入S03/多Agent冲突流程或hold。

## 6. 工具失败降级

### 只读工具失败
可以：重试一次、使用满足最低条件的fallback、复用仍有效的缓存/历史结果、请求专业Agent、降低置信度。

### Schema/验证工具失败
不能把“验证器没运行”当作“对象验证通过”。可执行静态人工检查，但必须标记验证层级。

### 状态读取失败
若状态决定动作资格，应hold；若只是增强信息，可降级继续。

### 动作能力不可用
不能由Agent-1自行假装执行。Task保持blocked/queued等真实状态，等待执行层恢复。

## 7. 降级结果必须显式

ContextPackage/Decision basis 应能表达：
- missing_requirements
- stale_requirements
- conflicting_sources
- fallbacks_used
- confidence_impact
- action_narrowing
- follow_up_requests

禁止后台悄悄换源而不留下证据。

## 8. 防无限收集

补信息请求必须满足：
- 会改变决策；
- 有现实来源；
- 能在有效时间内取得；
- 不与现有请求重复。

同一缺失信息连续请求失败后，应转为hold/降级/排除方案，而不是无限追问。

## 9. 业务无结果 ≠ 工具失败

例如：
- 查询无新Review：可能是有效的“0结果”；
- 查询接口报错：tool_error；
- 报表尚未生成：timeout_or_delay；
- 无权限访问：permission_denied。

只有准确区分，才能让后续S08和Learning正确理解结果。
