# S01 异常处理

## 目的
定义事件校验过程中遇到缺数据、格式错误、来源异常、对象不明、重复事件等情况时如何安全处理。

## 一、缺少关键字段
### 可修复
例如：
- facts中存在完整事实，但summary为空；
- product_id疑似格式错误但可通过其他字段推断对象；
- severity缺失但事件事实可保留。

处理：
- status = `needs_information` 或 `passed_with_warnings`；
- 明确 missing_information；
- 不自行虚构字段。

### 不可修复
例如：
- event对象不存在；
- source完全未知且没有来源凭据；
- 无法判断任何业务对象；
- occurred_at完全不可解析且事件依赖当前时效。

处理：`rejected`。

## 二、来源异常
来源不在允许列表：
- 若明显是配置尚未覆盖的新合法来源：`needs_information`/人工确认；
- 若来源伪装、无法解释：`rejected`；
- 若来源合法但超出专业边界：保留事件并输出 `SOURCE_SCOPE_MISMATCH`。

## 三、时间异常
### 未来时间
若 occurred_at 明显晚于当前时间：
- 检查时区；
- 无法解释则 warning 或 needs_information；
- 不自动改写原始时间。

### 旧事件
旧事件不等于无效：
- 若事件用于历史复盘，可以继续；
- 若事件声称当前状态，则必须复核新鲜度。

## 四、事实与摘要矛盾
例如 summary 写“库存已断货”，facts却显示可售库存200件。

处理：
- 不选择任何一边作为真相；
- 输出阻断或高等级警告；
- 要求补原始数据或来源 Agent 解释；
- 后续不得以高置信度使用该事件。

## 五、severity异常
severity与事实明显不一致时：
- 不静默修改来源字段；
- 输出 `SEVERITY_MISMATCH`；
- 后续由风险分级 Skill/状态识别重新判断。

## 六、重复事件
若 event_id完全相同：高度疑似重复。
若不同event_id但对象、类型、事实高度相似：可能重复。

处理：
- S01仅打 duplicate_signal；
- 不删除历史；
- 不自行合并事件；
- 交给事件处理模块决定去重/更新/合并。

## 七、外部依赖不可用
例如无法查询产品主数据、历史事件库不可用：
- 结构校验仍继续；
- 标记未完成的校验项；
- 若该依赖是关键，则 `needs_information` 或 `hold_for_review`；
- 不把“系统查不到”误判成“对象不存在”。

## 八、输入过大
若 facts 或附件数据过大：
- 不应在S01阶段完整推理全部内容；
- 保留摘要与引用；
- 将大数据交给后续上下文装载或专业Agent处理。

## 九、未知异常
遇到未定义异常：
- 返回保守状态；
- 记录异常类型和原始输入引用；
- 不吞掉错误；
- 不输出伪造的 passed。

## 核心原则
S01发生异常时优先保护决策链的数据质量：能修复就明确要求补充，不能确认就降低置信或暂停，无法解释的输入不得假装正常通过。
