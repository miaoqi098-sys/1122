# S05 异常处理 V1.1

- 只有一个可行方案：允许status=single_feasible_option，并说明其他路径为何被约束、证据或资源排除。
- 信息不足：优先生成information_first、experiment或合法observe，不凭空补事实。
- S04 decision_item缺关键问题定义：返回needs_information/redefine_problem，不在S05自行换题。
- S03存在blocks_decision冲突：不得假装冲突已经解决；只生成能够补证据或在冲突下仍安全成立的方案。
- 知识库无匹配：基于事实、目标和一般经营原则生成，降低来源确定性并记录generation_notes。
- 历史方案曾失败：不得直接复用；只有关键条件、状态、目标或执行方式发生变化时才可重新生成，并记录差异。
- 所有方案均触碰硬约束：status=no_feasible_option，next_action=redefine_problem_or_constraints；不得偷偷放宽底线。
- 方案高度重复：合并同一策略族，保留参数范围或代表方案，不为了满足数量制造重复项。
- 方案只有空泛动作：判定为不可执行，要求动作原子化。
- observe没有窗口/结束条件：视为不完整方案，不得用“继续观察”逃避决策。
- information_first无法说明信息如何改变决策：视为低价值数据请求，应删除或重写。
- success_criteria依赖不存在的数据：写入data_needed/preconditions，不假装未来可以自动验证。
- 动作需要审批但审批条件未知：保留为precondition，交S06/S07进一步处理。
- 方案差异只来自轻微参数变化：放入同一similarity_group并合并。
- derived_from缺失：允许在知识不足场景生成，但必须明确generation_notes，不能伪造来源。

## 核心原则
异常情况下宁可输出“一个方案”“先补决定性信息”或“当前无可行方案”，也不要制造虚假的多方案选择。
