# S07 判断规则 V1.1

## 一、标准编排链
```text
1. 读取Agent-1已选selected_option
2. 读取S06 eligibility / required_controls / approval
3. 拆分原子任务
4. 将required_controls转成真实任务/条件
5. 分配owner / executor / approver / validator
6. 建立depends_on / blocks / parallel_with / mutex_with
7. 检查循环依赖、互斥和资源冲突
8. 确定任务初始状态
9. 输出Task DAG给调度与执行层
```

## 二、每个任务只有一个清晰主动作
复杂动作必须拆分。`优化广告`、`改善Listing`、`控制库存`不是执行任务。

## 三、完整承接S05和S06
S05的actions、success_criteria、stop_conditions不得在S07丢失。

S06的required_controls、eligibility、approval_level必须转化为任务约束。尤其`eligible_with_controls`不得在控制措施未落地时直接生成ready执行任务。

## 四、风险控制必须任务化
required_controls至少应转为以下之一：control任务、monitoring任务、approval任务、start_condition、stop_condition或rollback任务。

仅把“注意库存风险”写在备注中不算落实控制。

## 五、角色分离
owner负责业务结果；executor真正执行动作；approver负责授权；validator负责验证。

四者可以偶尔是同一个主体，但语义必须分开记录。

owner必须来自Agent能力地图、执行器能力或明确人工角色；不能随意指定不存在的主体。

## 六、先建立Task DAG再决定执行关系
- depends_on：前置任务；
- blocks：本任务阻塞的后续任务；
- parallel_with：可并行；
- mutex_with：互斥。

循环依赖属于编排错误，必须拆解或重构。

## 七、业务优先级不等于点击顺序
S07保留S04 business_priority，但具体执行可能因前置控制、审批、数据收集而出现低优先级步骤先执行。

不得为了执行顺序方便而篡改business_priority。

## 八、审批门
需要审批的任务初始进入pending_approval。审批完成前不得进入ready/running。

审批角色和等级读取权限矩阵与S06输出，不在S07硬编码人员姓名。

## 九、blocked与failed必须分开
- blocked：尚未成功开始或继续，因为依赖、审批、资源、数据或互斥条件阻塞；
- failed：已经实际尝试执行但执行失败。

资源不足通常属于blocked/deferred，不应伪装为failed。

## 十、start / stop / rollback分离
- start_condition：什么时候允许开始；
- stop_conditions：运行中什么时候止损停止；
- rollback：执行后如何恢复状态。

三者不能混成一个“异常处理”字段。

## 十一、观察窗口必须进入任务结构
观察窗口不能留在聊天记忆中。monitoring/validation任务必须记录窗口、观测对象和结束触发条件。

观察窗口结束前，不因为轻微波动自动产生反向任务；需要结合S10策略防抖。

## 十二、success_criteria必须可验证
禁止“效果变好”“广告更健康”等模糊标准。

标准应尽量连接经营指标、基线、状态或明确执行结果。无法验证时不得直接进入执行。

## 十三、每个执行任务必须有validator
执行成功不等于经营成功。execution任务必须知道后续由谁验证，并最终进入S08。

## 十四、互斥任务处理
新任务与active_tasks互斥时不得直接覆盖旧任务。应冻结低优先级任务、等待旧任务结束，或交S03/S10判断策略冲突与反转合法性。

## 十五、S07不执行
S07只输出任务网络。定时、触发、重试、API调用、长期状态维护属于共享调度与执行层。

## 核心原则
S07的产物不是“待办清单”，而是一张可被调度器和执行器读取的施工图：动作明确、责任明确、依赖明确、控制明确、状态明确、验证明确。
