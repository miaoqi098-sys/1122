# S10 异常处理 V1.1

- 旧任务记录缺失：无法可靠防抖，回S02补历史/任务上下文，不得假装不存在旧策略。
- strategy_chain缺失：允许临时按active/recent tasks判断，但输出request_more_context；高频策略不应长期缺策略链。
- 观察窗口未定义：根据任务类型/配置请求补充，不随意假设统一天数。
- 新证据质量未知：evidence_delta=unknown，默认不足以直接override高风险策略。
- 原启动证据缺失：不能可靠比较evidence_delta，必要时回S02补决策上下文。
- 状态切换证据冲突：交S03处理，不自行认定state_change。
- 紧急保护条件触发：即使窗口未结束也不得机械hold。
- stop_condition触发但任务状态仍running：输出override并要求S07处理旧任务。
- 多个重复事件：merge为同一策略链证据更新，不把重复上报当独立强证据。
- 多Agent同时提出不同方向调整：先经S03聚合冲突，再由S10判断是否足以打断当前策略。
- 频繁小幅同方向调整：虽然不是full reversal，也可能形成慢性抖动；根据adjustment_count、间隔和窗口状态hold/escalate。
- 频繁部分反转：累积reversal_count并提高审查等级，不逐次当作独立正常微调。
- 旧任务数据库状态与真实执行状态不一致：优先核验真实状态，必要时回S02/执行层，不机械依赖running/completed标签。
- proposed_action缺direction/magnitude/scope：无法准确计算change_relation，request_more_context。
- target相似但实际对象不同：不得误合并策略链，先完成对象标准化。
- action_type不同但经营效果互相冲突：change_relation可标conflicting_action并交S03/S10联合判断。
- observation window已结束但S08尚未验证：可以解除机械hold，但不应把“窗口结束”直接当作换策略理由。
- trend只有单一低质量数据源：不得因连续值同方向就自动升级为stronger evidence。
- critical_new_fact来源未经核验：先核验事实，除非保护机制要求先停后查。
- override需要高审批但approval context缺失：decision=escalate/request_approval，不模拟审批通过。
- override_record无法确定旧任务处理方式：old_task_actions使用review，不擅自cancel/rollback。
- hold_until无法确定：允许为null，但必须提供release_conditions和review_trigger。
- review_at已过期但没有新数据：触发复核，不自动allow或override。

## 核心原则
S10异常处理的重点是：上下文不完整时不制造确定性；真正风险出现时不被防抖规则绑住；旧任务状态不可信时优先核验事实。
