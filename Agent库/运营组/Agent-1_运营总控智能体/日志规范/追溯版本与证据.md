# 日志追溯、版本与证据

## 1. 业务主键链
`event_id → decision_item_id → option_id → decision_id → task_plan_id → task_id → execution_result_id → validation_id → learning_id`

`strategy_chain_id`跨策略生命周期串联多次Decision/Task/Validation。

## 2. 运行trace边界
- run_id / trace_id / parent_run_id：一次运行尝试、Skill/Agent调用追踪。
- 业务主键：经营对象生命周期与复用。

禁止用run_id替代decision_id/task_id，也不能因重试产生新run_id就复制一整套业务对象。

## 3. 版本字段
对象发生有效修订时至少保留：
- object_id
- version/revision
- previous_version_ref
- changed_at
- changed_by/source
- change_reason
- evidence_refs

## 4. Evidence refs
重要判断与状态变化应尽量引用原始或标准化证据，而不是只留自然语言摘要。证据至少标识来源、时间、新鲜度、scope和可定位引用。

## 5. Scope
日志使用统一scope语义，不要求所有记录都有ASIN/product_id。跨scope聚合时保留每个source object的原scope。

## 6. Append-only与更正
发现旧日志事实错误时：
1. 不静默覆盖；
2. 新增correction/revision；
3. 指明旧记录、错误原因、新证据；
4. 更新effective/valid状态；
5. 保留审计链。

## 7. StrategyChain追溯
策略反转/替代时必须能回答：
- 被替代的decision/task是谁；
- 新证据是什么；
- S10结果是什么；
- 哪个版本开始生效；
- 旧结果为什么仍保留。

## 8. 运行边界
真实日志ID生成、存储、索引、trace关联和证据仓库属于未来运行/数据层；本文件只规定框架语义。
