# Agent-1 审批与升级规则

本文件定义 Agent-1 何时必须请求审批、审批上下文需要什么，以及权限/影响级别变化如何影响审批严格度。

## 1. 核心原则
审批与 `L0-L3` 权限/影响分类相关，但**不是同一个对象**。

最终审批要求通过当前正式决策链表达：
`S06 RiskAssessment → 必要时S10 → DecisionSelector → FinalDecision.approval → S07 Task审批节点`

因此禁止使用“动作=L2，所以必然审批”或“动作=L1，所以必然自动执行”作为唯一判断。

## 2. 无需审批的典型条件
只有同时满足以下条件，FinalDecision才可以形成无需额外人工审批的执行路由：
- 身份权限允许；
- 动作影响低且可逆；
- 处于明确授权范围；
- S06未返回requires_approval/prohibited/requires_more_evidence；
- required_controls完整；
- 数据与证据足够；
- 不存在S10 hold/escalate；
- 不违反hard constraints/合规要求；
- S07可以形成合法Task和验证计划。

## 3. 必须请求审批的典型条件
任一条件满足时，应在FinalDecision中表达`requires_approval`、approval requirements或`request_approval_context`：
- 动作超出当前授权范围；
- 高影响或难以恢复；
- 涉及账户、合规、资质、知识产权、产品安全；
- 涉及删除、结构性迁移、父子体重大变更；
- 风险评估明确要求审批；
- 专业证据重大冲突且仍决定继续高影响动作；
- 处于关键活动窗口且动作可能显著改变经营结果；
- 价格、预算、库存等变化规模超过当前授权边界；
- S10返回escalate；
- 规则明确要求人工授权。

## 4. 审批请求内容
至少包含：
- decision_id；
- scope；
- source event / decision_item refs；
- 当前经营状态与关键事实；
- selected_option与备选方案；
- why_selected / why_not_others；
- 主要风险与required_controls；
- 预计影响范围；
- success criteria；
- observation window；
- stop/rollback conditions；
- strategy_chain影响；
- 需要审批的具体动作/参数/边界。

不得强制所有审批请求填写product_id/ASIN；按scope表达。

## 5. 审批结果
允许：
- approved；
- approved_with_conditions；
- rejected；
- request_more_information；
- deferred。

“未回复”不是批准。

批准只授予指定范围内的执行资格，不代表Task已执行，更不代表经营结果成功。

## 6. 审批后的状态推进
- 批准：由S07/Scheduler按授权范围推进Task；
- 附条件批准：条件必须转为required_controls/Task约束；
- 拒绝：保持Decision历史，禁止对应执行Task；
- 请求补信息：回到明确resume_from补证据；
- 暂缓：进入pending/hold并保留review trigger。

若审批后事实、风险或范围发生重大变化，应重新评估，必要时重新请求审批。

## 7. 权限/影响等级上调
L0-L3可以因影响、不可逆性、冲突、活动窗口、合规等因素变化。上调代表更严格的风险与授权审查，**不自动产生固定审批结果**。

## 8. 紧急情况
商品不可售、账户健康或严重合规风险可提高事件severity/紧急处理优先度，并允许暂停与之冲突的低优先级计划；但不能因此突破身份权限或跳过必须的审批/证据门。

## 9. 禁止
- 固定“修改售价=L2=必须审批”作为全局唯一规则；
- 因L1标签就绕过S06/FinalDecision/S07；
- 把approval通过写成execution succeeded；
- 把未回复视为批准；
- 审批后执行超出批准范围；
- 用审批机制替代经营判断本身。
