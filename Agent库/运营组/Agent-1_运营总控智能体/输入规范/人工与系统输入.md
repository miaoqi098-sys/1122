# 人工与系统输入

## 1. 人工输入
人工输入可以是：
- 经营目标或优先偏好；
- 明确业务约束；
- 审批/拒绝；
- 对事实的修正；
- 对策略方向的授权；
- 临时经营指令。

人工输入必须区分：`fact / preference / constraint / approval / correction / instruction`。偏好、授权和指令不得伪装成客观事实。

建议至少保留：
- input_id；
- source_type = human；
- source_actor；
- input_kind；
- scope；
- content；
- occurred_at / received_at；
- related_event_id / decision_id（适用时）；
- evidence_refs（若属于事实修正）。

## 2. 系统输入
系统输入包括：
- 监控触发；
- Scheduler/Executor状态；
- Schema校验结果；
- 工具失败/数据源失败；
- 执行回执；
- 状态变更通知。

系统输入必须标明 `source_type = system` 和系统来源，不得直接等价为专业经营结论。

## 3. 进入链路
- 可解释为经营 Event 的人工/系统触发 → 标准化为 Event → S01；
- 审批/授权类输入 → 作为决策/任务上下文引用，不重复制造经营事实；
- 执行回执 → 进入 ExecutionResult/后续验证链，不包装成专业 Agent 结论；
- 工具失败 → 记录为缺失/失败状态，不把指标默认为0。

## 4. 优先级
人工输入不天然覆盖系统事实；系统输入也不天然覆盖人工业务约束。发生冲突时应按输入类型判断：
- 事实冲突 → 比较证据与新鲜度；
- 授权/审批 → 作为权限门；
- 业务目标/偏好 → 进入目标/约束上下文；
- 系统失败 → 触发缺失/降级，不产生虚假事实。

## 5. 禁止
- 用户说“我希望ACOS低于20%”就记录为“当前ACOS=20%”；
- API失败就记录“销量=0”；
- 审批通过就推断经营结果已成功；
- 人工修正事实没有来源/证据引用；
- 系统日志直接成为FinalDecision。
