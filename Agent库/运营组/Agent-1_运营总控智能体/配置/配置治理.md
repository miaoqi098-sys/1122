# 配置治理

## 1. 单一真源原则
配置文件不复制业务规则正文，只保存开关、引用、版本和允许覆盖的参数。规则正文仍以对应正式模块为真源。

## 2. 覆盖层级
推荐框架顺序：
1. 系统默认；
2. Agent-1默认；
3. account/store/global或具体scope覆盖；
4. 单次运行显式覆盖。

后层只能在权限允许范围内覆盖前层；硬约束、合规边界和canonical对象结构不可被普通覆盖取消。

## 3. 配置项分类
- `identity`：Agent身份与版本。
- `mode`：证据优先、历史/活动上下文要求等框架开关。
- `schemas`：canonical输入输出引用。
- `rule_refs`：决策/策略/审批/任务规则路径引用。
- `defaults`：无业务含义歧义的默认行为。
- `runtime_placeholders`：未来运行层注入占位，不包含密钥。

## 4. 优先级语义
`P0-P3`若保留，只能用于事件严重度/任务执行优先级等已有定义场景，不能在配置层定义固定business_priority。经营决策排序必须由S04根据目标、状态、证据、依赖与约束动态形成。

## 5. 审批语义
配置不得用固定L0-L3强行映射所有经营动作。审批需求由FinalDecision/S07基于规则、风险、权限和动作性质表达：
- requires_approval；
- approval requirements；
- request_approval_context；
- pending_approval。

配置可以声明“不可逆/合规动作默认需要审批”类布尔保护，但不能替代正式审批判断。

## 6. 阈值与业务参数
利润底线、库存安全、转化、价格、广告等业务阈值应归属经营指标库/目标系统/决策规则及未来机器配置，不在Agent根配置中散落硬编码。

## 7. 版本与兼容
- `config_version`用于配置合同版本。
- `compatible_agent_version`声明兼容Agent版本范围。
- deprecated字段应有迁移说明。
- 重大语义变化必须显式升级版本。

## 8. 运行边界
真实加载顺序、环境变量替换、远程配置、热更新、密钥管理和运行时Schema校验属于未来运行层。框架层只定义合同与边界。
