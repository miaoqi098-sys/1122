# 事件合并规则

## 1. 目的
把多个高度相关事件组织成一个可管理事件组，减少重复决策，同时避免粗暴丢失来源、差异和时间演化。

## 2. 可合并条件
通常需要同时满足：
- scope 相同或存在明确父子 scope；
- event_type 相同或属于同一经营问题；
- 时间窗口高度重叠；
- 合并后不会掩盖不同风险/资格；
- 对 DecisionItem 的核心问题定义一致。

## 3. 不应合并
以下情况应保持独立并建立关联：
- 属于不同经营治理优先层或服务于不同上层经营目标，且会形成不同决策冲突；
- 一个是合规风险、另一个只是增长机会；
- 不同 scope 需要不同动作；
- 证据方向明显冲突；
- 一个事件已 resolved/closed，另一个是新周期重新发生；
- 合并会导致严重度、deadline、责任方或控制条件被模糊。

> 当前目标系统对 `goal_layer` 存在双重语义冲突，本文件不再把 `goal_layer` 作为唯一合并判断字段。待 `CONFLICT-A1-TARGET-001` 解决后，应使用正式统一字段（预计区分 goal_hierarchy 与 governance_layer）。

## 4. 合并结果
建议形成：
- canonical_event_id；
- merged_event_ids[]；
- source_refs[]；
- evidence_refs[]；
- first_seen_at / last_seen_at；
- merged_summary；
- preserved_differences[]；
- current_severity；
- scope；
- merge_reason。

原 event_id 不得删除。

`merged` 属于 processing_disposition，不是长期 event_status。

## 5. severity 合并
不得简单取最大值或平均值。应根据最新证据、影响范围和当前状态重新判断，并记录为什么当前 severity 成立。

## 6. 与 DecisionItemBuilder
一个事件组可以形成一个 DecisionItem，也可以在保留同一 canonical event/group 引用的前提下拆成多个 DecisionItem。是否拆分取决于是否存在不同问题、目标、约束、动作边界或证据冲突。

输出给 DecisionItemBuilder 时应以 `ProcessedEvent.schema.json` 的事件治理结果为标准承载对象；DecisionItemBuilder 是否正式声明 ProcessedEvent 输入依赖仍需跨模块验证。

## 7. 禁止
- 为了减少数量把所有同 ASIN 事件合成一个；
- 合并后丢失来源 agent 和 evidence_refs；
- 通过合并隐藏冲突证据；
- 用尚未统一语义的 goal_layer 作为唯一合并依据；
- 合并后重复生成与原事件完全相同的 DecisionItem。
