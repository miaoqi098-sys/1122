# 事件处理示例与静态验收

## 示例A｜同一广告异常重复上报
Agent-4 在10分钟内重复上报同一关键词、同一窗口、同一事实。

正确处理：fingerprint 命中候选后仍做最终判断；第二条 processing_disposition=exact_duplicate，保留新 event_id/source_ref 并指向 canonical_event_id；无新证据则不重复触发 DecisionItem。

## 示例B｜同一问题出现新证据
原事件 P2，后续发现 scope 从单 ASIN 扩散到整个店铺。

正确处理：processing_disposition=update_existing 或建立强关联新事件；severity 可升级并记录 change_reason/evidence_refs，不得压成普通重复。

## 示例C｜合规风险与增长机会同时发生
两事件同 ASIN，但经营治理层、风险性质和动作方向不同。

正确处理：保持独立并建立 same_scope/可能冲突关系，不合并成单一平均事件；后续由 S03/S04 处理冲突和优先级。

## 示例D｜已关闭事件再次发生
前一周期库存风险已关闭，一个月后再次发生。

正确处理：若是新周期独立事实，创建 new_event 并建立 directed follow_up 关系；若确属原事件延续，则 transition_type=reopen，event_status 回到 open/monitoring。

## 示例E｜P0事件与DecisionItem优先级
账户风险 Event severity=P0。

正确处理：快速进入事件链并可能触发 Priority Gate；但对应 DecisionItem 仍由 S04 形成 business_priority，不能简单复制 severity 字段。

## 示例F｜Task完成但事件未解决
某广告结构调整 Task 已 completed，但两天后的核心指标仍未恢复。

正确处理：Task completed 不自动改变 Event；event_status 保持 monitoring/open，直到存在 resolution_evidence_refs / validation_refs 支持 resolved。

## 示例G｜动作失败但问题自然恢复
促销修复动作执行失败，但平台侧异常自行恢复。

正确处理：resolution_basis=natural_recovery，不得标记 action_effect_verified，不得把自然恢复归功于失败动作。

## 示例H｜merged与closed同时成立
事件B已被事件A承接，B不再需要独立追踪。

正确处理：B.processing_disposition=merged，同时 B.event_status 可进入 closed；证明处理结论和生命周期状态不是同一个枚举。

## 示例I｜dependency方向
事件A的处理必须等待事件B的库存数据确认。

正确处理：记录 source=A、target=B、relation_type=dependency、direction=directed；统一解释为“A依赖B”，不得在其他模块反向解释。

## 示例J｜指纹碰撞但并非重复
两个事件 scope、event_type、subject、时间桶相同，但一个是新出现的 critical_new_fact。

正确处理：fingerprint 只把它们放入候选集；最终判断为 update_existing 或 new/related event，不能自动 exact_duplicate。
