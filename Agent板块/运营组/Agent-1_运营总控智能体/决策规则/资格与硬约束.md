# 资格与硬约束

## 1. 定位
本规则把 S06 `eligibility` 转换为进入 DecisionSelector 前的正式资格门。它回答“该 Option 是否允许被最终选择”，不负责生成风险评分本身。

## 2. eligibility 处理
- `eligible`：可进入最终比较。
- `eligible_with_controls`：可进入比较；若被选中，`required_controls` 必须进入 FinalDecision 并由 S07 转成前置/伴随任务。
- `requires_approval`：不得直接自动执行；FinalDecision 必须保留审批要求、审批对象和审批前禁止动作。
- `requires_more_evidence`：不得形成高置信执行型 FinalDecision；应请求证据、缩小动作、转观察或重新生成方案。
- `prohibited`：不得进入最终候选集，不得通过“收益更高”覆盖。

## 3. 硬约束来源
硬约束可来自：
- 合规/账户安全；
- 商品可售资格；
- 明确禁止动作；
- 平台/政策限制；
- 库存或现金底线；
- 不可接受的最坏情况；
- 既有审批要求；
- 当前策略链 guardrail/stop condition；
- ContextPackage 中已确认 constraint_refs。

## 4. 硬约束分级
硬约束不得全部扁平化为同一种 block。至少区分：

### `absolute_block`
绝对禁止继续。典型包括明确违规、账户/商品不可执行资格、平台禁止动作、不可接受且无法控制的重大不可逆风险。

处理：相关 Option 进入 `prohibited`，不得通过审批或收益比较覆盖。

### `conditional_block`
当前条件下不可执行，但在恢复条件满足后可重新评估，例如库存、现金、价格保护或依赖条件未满足。

处理：记录 `release_conditions`，条件恢复前不得正常执行。

### `approval_gate`
业务方向可以成立，但动作影响或权限要求必须先审批。

处理：进入 `requires_approval`，审批前禁止相关执行 Task。

### `control_required`
风险可接受，但必须有明确控制条件。

处理：进入 `eligible_with_controls`，`required_controls` 必须完整传递。

### `temporary_protection`
在活动窗口、观察期、策略保护期等临时场景限制扩大/反转动作，不等同永久禁止。

处理：记录 `protection_window`、`release_conditions` 与 `review_trigger`。

## 5. dominant-risk override
当 S06 判定存在合规、账户、不可售、禁止行为或重大不可逆风险时，可触发 dominant-risk override。此时不得用多个低风险维度的平均结果稀释主导风险。

## 6. 控制条件传递
若选择 `eligible_with_controls`：
1. FinalDecision 必须引用对应 risk_assessment；
2. required_controls 不得在选择阶段丢失；
3. S07 必须把必要控制编排为前置、伴随或验证任务；
4. 控制无法落地时，该 Option 资格应退回重新评估。

## 7. 资格变化
eligibility 可以随新证据、状态变化或控制能力变化而改变，但必须：
- 保留上一次风险评估引用；
- 说明触发变化的新证据；
- 禁止无新证据自行从 prohibited/requires_more_evidence 升级为 eligible；
- 对 conditional_block / temporary_protection 明确记录解除条件；
- 若资格变化使已 active 的 FinalDecision 不再成立，按 `决策生命周期规则.md` 进入 invalidated/superseded 流程。

## 8. 禁止
- 先选方案，再倒推风险资格；
- 通过提高置信度覆盖 prohibited；
- 未落实 controls 就把 eligible_with_controls 当作 eligible；
- 把审批当作普通提示后继续自动执行；
- 用单一收益指标覆盖硬约束；
- 把所有硬约束都标记成 absolute_block；
- 没有 release_conditions 的临时阻断长期悬置。
