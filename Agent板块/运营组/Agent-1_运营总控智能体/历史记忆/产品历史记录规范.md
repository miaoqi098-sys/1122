# 产品与经营事实历史记录规范

## 1. 定位
本文件记录“真实发生了什么”，不负责生成经验结论。事实历史可来自Event、平台状态、价格/库存/广告/内容变更、活动、系统状态和其他可追溯事实。

## 2. 统一作用域
历史记录不再只绑定产品/ASIN，正式使用 `scope`。可覆盖：product、parent_product、sku、account、store、global、campaign、ad_group、keyword等。

## 3. 建议字段
每条事实历史至少应尽量保留：
- history_id
- scope
- occurred_at
- recorded_at
- category
- fact_type
- fact_summary
- before_state / after_state（适用时）
- source_event_ids[]
- evidence_refs[]
- source_type / source_ref
- data_window（适用时）
- confidence / evidence_quality（适用时）
- valid_until（若事实解释具有时效）
- related_decision_ids[] / task_ids[]（适用时）
- metadata

## 4. 典型事实类别
- 价格、参考价、促销变化；
- Coupon/BD/LD/站外活动时段；
- 广告设置与关键表现变化；
- Listing/A+等内容变更；
- 变体关系变化；
- 库存、补货、在途、入仓异常；
- 合规/资质/账户绩效；
- 评价/退货/VOC变化；
- 竞品/市场事件；
- 经营状态/目标的已确认切换；
- 系统/数据源重要可用性事实。

## 5. 事实与解释分离
字段 `fact_summary/before_state/after_state` 保存事实；“为什么发生”“未来应该怎么做”“这个策略有效”不应直接写入事实历史，分别由解释、Decision、Validation和LearningRecord承载。

## 6. 时间与活动上下文
活动期、正常期、断货期、改版期等必须保留上下文，避免未来把不可比窗口机械对比。

## 7. 失败记录
真实失败、异常和无效果事实不得删除。后续可以增加新状态/解释，但不能覆盖旧证据。

## 8. 复用原则
- 历史是ContextPackage候选上下文，不是每次全部装载；
- valid_until过期的解释不能当当前事实；
- 旧数据窗口与当前经营状态不一致时降低直接复用权重；
- 出现冲突记录时保留双方并交S02/S03/后续证据判断。

## 9. 禁止
- 在事实历史内混写`lesson`作为永久结论；
- 用received/recorded时间替代occurred_at；
- 账户级历史伪造ASIN；
- 新记录覆盖旧记录而不保留版本/来源。
