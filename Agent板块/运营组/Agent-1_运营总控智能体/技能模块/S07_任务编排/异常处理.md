# S07 异常处理 V1.1

- 无明确owner：任务保持created/blocked，不随意指定Agent。
- 无明确executor：可以完成任务规划，但不得进入ready；标记blocked并请求执行能力映射。
- 需要审批但approver/权限未知：进入pending_approval，不宣称可执行。
- S06 eligibility=prohibited：不得生成正常execution路径；计划应reject或仅保留调查/恢复类任务。
- S06 eligibility=requires_more_evidence：优先生成data_collection任务，不直接生成高风险执行任务。
- S06 eligibility=eligible_with_controls但required_controls未落地：execution任务不得ready。
- required_controls无法转成真实任务/条件：视为编排不完整，不能假装风险已经受控。
- 依赖形成循环：标记编排错误，必须拆解或重构Task DAG。
- 依赖任务不存在：记录unresolved_dependencies，不伪造task_id。
- success_criteria不可测：不得进入执行，先补指标或validation设计。
- 无回滚能力的高风险动作：提高审批要求并强化停止/监控条件；是否允许继续依权限和S06结论决定。
- 现有任务冲突：交S03/S10确认，不直接覆盖旧任务。
- mutex任务同时被安排ready/running：视为编排错误，冻结其中一个或重新编排。
- 截止时间未知：允许用观察窗口、事件触发或start_condition替代伪造日期。
- 执行资源不足：任务保留并标记blocked/deferred，不删除任务。
- executor尝试执行后失败：状态为failed，不得写成blocked。
- 前置依赖未完成导致无法执行：状态为blocked，不得写成failed。
- monitoring任务没有观测对象或窗口：视为不完整监控任务。
- rollback没有明确恢复目标：不得把“回滚”作为形式字段；需要补恢复动作。
- task_type与action不一致：例如approval任务却携带真实业务变更动作，视为编排异常。
- 同一个复杂action被原样塞入一个任务：必须进一步原子化。
- 调度/执行细节缺失：S07只记录需求与约束，不自行模拟定时器或API已经执行。

## 核心原则
编排异常时宁可让任务停在created/blocked/pending_approval，也不能为了让流程“看起来走通”而虚构执行能力、审批通过、依赖完成或风险控制已落实。
