# S08 异常处理 V1.1

- baseline缺失：不能可靠做前后比较，business_outcome=not_evaluable，overall=inconclusive，并请求补历史基线。
- success_criteria缺失：任务设计不完整，退回S07修正，不事后临时创造成功标准。
- actual_execution缺失：execution_status=unknown，不能假设动作已执行。
- 执行失败：failure_type=execution_failure，通常不能进一步认定strategy_failure。
- 观察窗口未开始：不评价经营效果。
- 观察窗口未结束：failure_type可为premature_evaluation，通常continue_observation。
- 观察窗口被重大事件破坏：status=invalid，重新建立比较窗口或输出inconclusive。
- 数据延迟：降低freshness并延后验证，不把未回传当0。
- 数据缺口集中在关键日期：降低completeness/quality，即使总样本量看似足够也不能忽略。
- 多动作重叠：加入confounders并降低attribution_status/confidence。
- 外部重大事件：标记external_confounding，必要时分段或重新建立比较窗口。
- 执行日志与实际状态不一致：优先核验真实状态，不能只信“API返回成功”。
- primary改善但guardrail breach：不得判整体success，必要时rollback_triggered。
- stop_condition触发：优先停止/回滚，不等待完整窗口来证明风险更严重。
- observed_results为0但数据源异常：按data_failure处理，不当成真实0。
- baseline与observed_results口径不同：窗口invalid或criterion not_evaluable，禁止直接比较。
- 指标定义/单位不一致：先标准化，无法标准化则not_evaluable。
- positive结果但同期BD/Coupon/价格变化：允许business_outcome positive，但归因降为weak/confounded。
- concurrent_events为空但已知存在其他执行任务：视为上下文不完整，不能给strong attribution。
- strategy_failure证据不足：使用inconclusive，不为了形成结论强行失败分类。
- failure_type同时存在多个候选：记录主要failure_type，并在validation_summary说明次要因素。
- S08发现需要新方案：只输出adjust/rediagnose，不直接越权生成并执行新策略。

## 核心原则
验证异常时优先保护“事实真实性”和“归因可信度”。宁可输出inconclusive，也不能把执行失败、数据缺失或外部干扰错误写成策略成功/失败。
