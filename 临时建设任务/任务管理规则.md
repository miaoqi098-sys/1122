# 临时建设任务管理规则

## 1. 主任务编号
主任务按执行顺序编号：
`任务1 → 任务2 → 任务3 → ... → 任务N`

主任务编号一旦进入执行阶段，不因后续发现问题而整体重排。新增问题优先作为当前任务的子任务处理。

## 2. 子任务编号
执行 `任务X` 时发现需要先解决的新问题，创建：
- `任务X-1`
- `任务X-2`
- `任务X-3`
- ...
- `任务X-N`

如果某个子任务继续发现更深问题，允许：
- `任务X-2-1`
- `任务X-2-2`
- ...

原则上最多建议三层；如果继续膨胀，应重新检查当前主任务是否定义过大。

## 3. 插入规则
发现新问题时先判断：

### A. 属于当前任务完成所必须解决
→ 插入当前任务子任务，并阻塞主任务完成。

### B. 与当前任务相关但不影响其框架完整性
→ 记录到后续最合适主任务，不阻塞当前任务。

### C. 属于真实运行实现
→ 记录到 `运行依赖待办.md`，不插入当前施工链。

### D. 属于正式架构之外的新想法
→ 先记录，不立即扩建正式架构；等待用户确认后再加入任务总表。

## 4. 执行顺序
默认严格执行：
```text
任务1完成
→ 任务2
→ 任务2-1
→ 任务2-2
→ ...
→ 任务2全部复核完成
→ 任务3
```

子任务按发现顺序编号，但可根据依赖关系调整子任务内部执行先后；编号不回收、不复用。

## 5. 状态
### 待执行
已进入队列但尚未开始。

### 执行中
当前正在排查、设计或修改。

### 被子任务阻塞
主任务本体已发现必须先处理的问题。

### 待复核
内容已修改完成，需要做一致性与边界验收。

### 已完成
符合本任务的框架完善标准，且无未完成阻塞子任务。

### 暂缓
用户明确要求暂时不继续。

### 取消
任务已确认不再需要。

## 6. 完成判定
主任务完成必须同时满足：
1. 主任务范围内文件已逐项排查；
2. 已知结构缺口已补齐；
3. 规则和接口无重大内部冲突；
4. 与已完善模块的连接关系一致；
5. 必须的Schema/字段规范已形成；
6. 示例、测试或验收标准达到框架层要求；
7. 所有 `任务X-*` 阻塞子任务已完成；
8. 真实运行依赖已单独记录，而不是混入当前完成标准；
9. 做过最终静态复核；
10. 用户未要求继续扩展本模块。

## 7. 框架完成 ≠ 实际运行完成
本阶段只要求：
`设计正确 + 内容完整 + 接口清楚 + 可供未来运行层实现`

不要求：
`代码已运行 + API已接入 + 数据库已上线 + 自动化已执行`

因此“无法真实运行”本身不能无限阻塞Agent库框架完善。

## 8. 任务粒度原则
每个主任务最好对应一个能够独立验收的模块或Agent。

不要把：
- 一个字段改名；
- 一个例子补充；
- 一个README小修；

直接升级成新的主任务。此类事项通常应作为当前任务子项处理。

## 9. 修改正式架构的规则
临时任务区只负责管理建设，不取代正式架构文档。

实际完成的规则、Schema、README、测试等必须写回正式位置，例如：
`Agent库/运营组/Agent-1_运营总控智能体/...`

不得只在本目录写“已经完善”，却不修改正式模块。

## 10. 复核原则
每完成一个主任务，必须至少复核：
- 名称是否一致；
- 职责是否重复；
- 输入输出是否断裂；
- 旧规则是否冲突；
- 是否不小心越界进入运行层；
- 是否产生新的后续阻塞项。

## 11. 当前施工主线优先级
当前固定优先级：
1. Agent-1本体完整；
2. Agent-2至Agent-13逐个完整；
3. Agent之间接口与协作一致；
4. Agent库全局静态验收；
5. 再讨论是否转共享基础设施/运行建设。

## 核心原则
施工时允许不断发现问题，但不能让新问题把建设路线无限发散。当前任务的问题就收在当前任务下面；运行问题单独挂账；当前任务真正收干净后再走下一项。
