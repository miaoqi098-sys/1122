# 阻塞任务池

> 本文件集中管理 Agent库 无人值守施工中暂时无法安全继续的任务。阻塞不等于停止施工；可绕行的任务必须继续推进其他不依赖项。

## 1. 进入阻塞池的条件

满足任一条件可进入：
- 需要用户业务选择，且不同选择会明显改变架构；
- 缺少无法从仓库、已有规则或上下游文件推导的信息；
- 涉及删除正式目录、批量重命名、推翻统一Schema等高影响变更；
- 连续两次执行失败且没有新证据；
- 任务之间形成循环依赖；
- 需要真实运行层能力才能继续定义关键接口；
- 仓库状态异常，继续写入可能造成破坏。

## 3. 阻塞绕行规则

```text
任务A阻塞
↓
记录到阻塞池
↓
检查依赖图
├─ 后续任务依赖A → 一并标记等待
└─ 后续任务不依赖A → 继续施工
```

不得因为一个局部任务阻塞就停止整个 Agent、整个模块或整个 Agent库。

## 4. 每小时复核规则

每次自动施工唤醒时：
1. 读取全部未解除阻塞项；
2. 检查仓库是否出现新证据或相关任务是否已补齐前置条件；
3. 只有存在新证据时才允许重新尝试；
4. 无新证据时不重复执行、不重复分析；
5. 每小时汇报中持续累计显示未解决阻塞项。

## 5. 阻塞解除

解除前必须明确：
- 新证据是什么；
- 原阻塞条件为何消失；
- 是否需要重新分析；
- 恢复后返回哪个任务。

解除后：
- 从 `🟨 被阻塞` 改为 `⬜ 待分析` 或 `⬜ 待执行`；
- 更新 `任务总表.md` 当前指针；
- 保留历史阻塞记录，不删除。

## 6. 循环依赖处理

若发现：
`A → B → C → A`

必须：
1. 记录完整循环链；
2. 选择最低优先级、最低风险或最可延后的一项进入阻塞；
3. 禁止三项无限互相唤醒；
4. 继续处理不依赖该循环链的其他任务。
