# 系统总工程蓝图 V1

> 状态：V1 总体架构规划
> 目标：从“单个 Agent 工程”提升到“完整亚马逊智能经营系统工程”视角。
> 原则：先确定总工程边界、层级、核心对象与依赖关系，再继续纵向深挖具体 Agent / Skill / 执行器。
> 当前不执行大规模目录迁移；现有 Agent-1 等工程保持原位，后续按蓝图逐步映射与迁移。

---

## 一、系统最终目标

系统不是一组互相独立的 Agent，也不是单纯的 Amazon 数据仪表盘。

系统最终应形成一条可以真实运行、追溯和复盘的经营闭环：

```text
真实世界 / Amazon / 第三方平台
            ↓
        对外连接
            ↓
      数据采集与标准化
            ↓
      产品经营状态识别
            ↓
      事件 / 异常 / 机会
            ↓
专业 Agent + Skill 分析判断
            ↓
       Agent-1 总决策
            ↓
      Decision / Goal
            ↓
         Task
            ↓
     是否需要人工介入？
       ┌────┴────┐
       是         否
       ↓           ↓
  人工审批/处理   自动执行
       └────┬─────┘
            ↓
      ExecutionResult
            ↓
       结果验证 / 复盘
            ↓
      Knowledge / Memory
            ↓
       更新经营状态
            ↓
       UI 经营指挥中心
```

核心要求：
- 看得见真实经营状态；
- 系统能够发现问题和机会；
- Agent 能够分析和决策；
- 决策能够转化为任务；
- 在权限允许时能够真实执行；
- 不允许自动执行时转成人工任务；
- 所有操作可追踪、可解释、可回滚或可验证；
- 结果能够回写为长期记忆与可复用知识；
- UI 最终展示的是完整经营系统的结果，而不是孤立数据。

## 四、第二层：业务能力层

业务能力先于 Agent 存在。

Agent 是“谁负责分析和判断”，Skill 是“它会什么”，业务能力是“系统必须具备什么经营能力”。

当前运营域至少包含：

```text
运营业务能力
├── 产品经营
├── 库存物流
├── 站外推广
├── 竞品经营
├── 广告经营
├── 流量与转化
├── 价格与促销
├── 利润与经营
└── 消费者体验
```

注意：其中产品、库存物流、站外推广、竞品、广告已确定为运营 UI 二级板块；流量与转化、价格与促销、利润与经营、消费者体验当前确定在产品三级 UI 中展示。

每项业务能力后续都需要回答六个问题：
1. 需要什么输入数据；
2. 如何判断状态；
3. 会产生什么事件；
4. 由谁分析和决策；
5. 能产生什么任务/操作；
6. 如何验证结果。

## 五、第三层：Agent / Skill 智能层

### Agent

Agent 负责角色、目标、职责、分析、判断、决策和协作。

运营组当前架构：
- Agent-1：运营总控智能体，唯一总控决策中枢；
- Agent-2 ～ Agent-13：专业领域智能体。

Agent-1 只是总工程中的一个高价值颗粒，不代表整个系统。

### Skill

Skill 是 Agent 可复用的能力单元，例如：
- 事件校验；
- 上下文装载；
- 冲突检测；
- 决策排序；
- 方案生成；
- 风险评估；
- 任务编排；
- 结果验证；
- 经验沉淀；
- 策略防抖。

原则：
- Agent ≠ Skill；
- Skill ≠ Tool；
- Tool ≠ Connector；
- Agent 调用 Skill；
- Skill 可调用 Tool；
- Tool 通过 Connector / API 连接真实世界。

## 七、第五层：数据 / 知识 / 记忆 / 政策治理

### 数据 Data
回答“现在真实发生了什么”。

例如：销量、Sessions、CVR、广告花费、CPC、库存、价格、Review、退款等。

### 知识 Knowledge
回答“系统普遍知道什么”。

例如：广告匹配逻辑、库存风险规则、Amazon促销机制、经营诊断知识、策略模板。

### 记忆 Memory
回答“这个具体产品过去发生过什么”。

例如：为什么三天前提高预算、某关键词过去30天排名变化、某次策略调整后的结果。

### 政策 Policy / Boundary
回答“什么可以做、什么不可以做、谁有权做”。

包括：
- 平台政策；
- 合规边界；
- Agent权限；
- 自动执行权限；
- 人工审批要求；
- 高风险/不可逆动作限制。

政策边界是全系统横切约束，不只属于风险 Agent。

### 为什么不把 UI 十大一级板块机械地全部做成根目录

UI 导航是“用户如何进入系统”，工程根目录是“代码、规则、数据、Agent、运行能力如何组织”。两者必须可映射，但不应该强行一一相等。

例如：
- UI 的“Agent板块”映射到工程 `02_Agent系统/`；
- UI 的“技能板块”映射到工程 `03_技能系统/`；
- UI 的“任务中心”映射到工程 `04_任务中心/`；
- UI 的“知识板块”映射到工程 `08_知识系统/`；

## 十三、下一阶段工程顺序

推荐顺序：

```text
总工程蓝图 V1
      ↓
首页需求反向拆解
      ↓
核心业务能力地图
      ↓
核心对象 / Schema 统一
      ↓
现有工程目录映射与缺口清单
      ↓
选择一个真实产品作为纵向 MVP
      ↓
打通 Data → Event → Agent → Decision → Task
      ↓
打通 Approval / Execution → Validation → Memory
      ↓
驱动 UI 产品状态卡
      ↓
再扩展更多产品、更多 Agent、更多业务能力
```

### 当前最重要的工程原则

1. 不再以“做完某个 Agent”代表“系统完成度”。
2. 新增工程必须能放入总蓝图中的明确位置。
3. UI 需求必须能反向追溯到底层对象与数据来源。
4. Agent 只承担 Agent 应有的职责，不吸收任务、执行、数据、记忆、API 等公共基础设施职责。
5. 优先打通纵向闭环，再扩大横向模块数量。
6. 当前 Agent-1 保留现有成果，待核心对象和跨层接口明确后再继续深挖。
7. 系统运行实现、真实 API、生产执行权限仍需单独规划和授权，不因本蓝图建立而自动开启。
