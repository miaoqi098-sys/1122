# 首页六大区域 → 后台工程需求反向拆解 V1

> 状态：V1 已完成首轮反向拆解
> 上位文档：`系统总工程蓝图/README.md`
> UI依据：`UI界面设计板块/README.md`
> 目的：从首页最终要展示的真实经营结果，反向确定后台必须具备的数据、对象、Agent、Skill、任务、执行、权限、日志、连接与基础设施。
> 边界：本文件定义“后台必须建设什么”和“各部分如何连接”，不代表本轮已实现真实 API、数据库、调度器或生产执行权限。

---

## 一、反向拆解原则

首页不是独立的数据页面，而是整个经营系统的压缩结果。

任何一个首页字段，都必须能够回答以下问题：

1. 这个字段对应哪个系统核心对象？
2. 原始数据来自哪里？
3. 谁负责生产/计算这个结果？
4. 是否需要 Agent 判断？如果需要，是哪个 Agent？
5. 是否需要 Skill / Tool？
6. 结果多久更新一次？
7. 数据延迟、缺失或冲突时如何显示？
8. 用户点击后进入哪个业务对象或任务？
9. 是否涉及权限、审批、自动执行？
10. 这个结果是否能追溯到真实证据、决策、任务和执行记录？

首页六大区域最终共同依赖一条统一主链：

```text
外部真实世界
    ↓
Connector / API / 文件
    ↓
Raw Data
    ↓
标准化 Data / Metric
    ↓
BusinessState / Event
    ↓
Agent + Skill
    ↓
Decision / Goal
    ↓
Task / Approval
    ↓
Action / Execution
    ↓
ExecutionResult / Validation
    ↓
Memory / Knowledge
    ↓
首页聚合与产品状态卡
```

# 二、区域 01：左侧全局导航

## 2.1 UI要回答的问题

- 系统有哪些一级业务入口？
- 当前用户能进入哪些板块？
- 当前所在页面属于哪个一级/二级/三级模块？
- 用户没有权限时如何处理？

## 2.2 后台核心对象

```text
ModuleDefinition      模块定义
RouteDefinition       路由定义
NavigationNode        导航节点
Permission            权限
Role                  角色
FeatureFlag           功能开关
```

其中 `Permission` 已在总蓝图中属于政策/权限体系；其余对象属于 UI 与系统公共配置，需要后续纳入统一对象体系。

## 2.3 后台工程需求

### 必须具备
- 模块注册表：一级、二级、三级模块统一编号和名称；
- 页面路由表：导航节点对应真实页面；
- 权限映射：用户/角色可见、可读、可操作范围；
- 功能开关：尚未建设完成的模块可以显示“建设中”或隐藏；
- 导航版本管理：UI架构升级时可追溯；
- 面包屑/当前上下文：知道用户当前处于哪个业务对象和产品。

### 不应该交给 Agent
导航属于确定性系统配置，不需要 Agent-1 或专业 Agent 每次判断。

Agent 只可能影响“某个功能是否因风险被临时禁止操作”，但最终仍由权限/政策系统执行。

## 2.4 主要工程归属

```text
11_UI界面设计板块
15_系统公共层
06_政策边界
12_系统运行层（页面上下文）
```

## 2.5 当前仓库覆盖判断

- UI导航结构：已有 V1 规划；
- 系统公共层：已有“配置/权限”框架；
- 正式 ModuleRegistry / Route / FeatureFlag Schema：未建立；
- 真实用户权限服务：未实现。

## 2.6 首页MVP要求

第一阶段可以使用静态模块配置，不需要先做复杂动态导航系统。

但必须从一开始保留：
- `module_id`
- `route_id`
- `required_permission`
- `status`

避免未来 UI 与后台模块名称靠人工硬编码关联。

# 三、区域 02：今日经营概览

## 3.1 UI要回答的问题

当前已经确认首页至少显示：
- 今日销量/销售；
- 今日花费；
- 今日利润。

其本质不是三个数字，而是一个可信的“今日经营快照”。

## 3.2 后台核心对象

```text
Product
Marketplace
SellerAccount
Metric
MetricSnapshot
Cost
Revenue
AdSpend
ProfitSnapshot
DataFreshness
DataSourceRef
```

建议后续在核心对象中增加 `MetricSnapshot`、`DataFreshness`、`DataSourceRef`，因为首页显示实时/准实时数据时，必须知道数字的时间和来源。

## 3.3 原始数据来源

### 销量 / 销售
可能来自：
- Amazon SP-API；
- Seller Central 报表；
- 订单/销售报表；
- 暂时阶段也可由人工文件导入。

### 广告花费
可能来自：
- Amazon Ads API；
- 广告报表文件。

### 利润
不能只靠 Amazon 单一接口，至少可能依赖：
- 销售收入；
- 广告花费；
- FBA费用；
- 佣金；
- 采购成本；
- 头程/物流成本；
- Coupon/促销成本；
- 退款/退货损失；
- 其他成本配置。

## 3.4 数据处理链

```text
SP-API / Ads API / 财务成本
          ↓
      原始数据
          ↓
数据标准化 + 币种/时区处理
          ↓
    MetricSnapshot
          ↓
 店铺级 / 产品级聚合
          ↓
    ProfitSnapshot
          ↓
      首页展示
```

## 3.5 必须解决的系统问题

### A. “今日”定义
必须统一业务日期和时区。

建议未来统一字段：
- `marketplace_timezone`
- `business_date`
- `window_start`
- `window_end`

不能让广告数据按一个时区、订单数据按另一个时区计算“今日”。

### B. 数据延迟
Amazon 各数据源并非同时更新。

首页每个指标必须携带：
- `collected_at`
- `effective_at`
- `freshness_status`
- `source`

建议状态：
```text
fresh       最新
lagged      有延迟
partial     部分数据未齐
stale       已过期
error       拉取失败
```

### C. 利润不是简单销售额减广告费
必须由 Agent-6/利润财务域未来使用统一利润口径，但“利润计算公式本身”应是业务/数据规则，不应藏在 Agent Prompt 中。

## 3.6 Agent / Skill职责

### Agent角色
- Agent-6：利润财务分析；
- Agent-5：流量结构分析（如首页后续出现流量指标）；
- Agent-1：不负责生产基础指标，只在指标异常影响经营决策时使用这些数据。

### Skill / 服务
未来至少需要：
- 数据标准化；
- 指标聚合；
- 利润计算；
- 数据完整性检查；
- 数据新鲜度判断；
- 币种转换（多站点后）；
- 时间窗口对齐。

## 3.7 主要工程归属

```text
07_数据系统
10_对外连接
01_业务系统/运营板块
02_Agent系统/Agent-5、Agent-6
03_技能系统
15_系统公共层/配置与监控
```

## 3.8 当前仓库覆盖判断

- 数据接口层：已有 SP-API / Ads API / 文件导入 / 标准化的框架定义，但目前仍是框架级；
- 记忆与数据层：已有产品主数据和历史数据规划，但尚未形成统一 MetricSnapshot；
- Agent-6：有角色架构，但不能替代数据系统；
- 今日销售/花费/利润统一快照：系统级缺口。

## 3.9 首页MVP要求

V0可先支持：
- 一个站点；
- 一个币种；
- 今日销售额；
- 今日广告花费；
- 今日估算利润；
- 每个指标明确显示更新时间和数据状态。

宁可显示“利润为估算值 / 数据延迟”，也不能展示无法追溯来源的精确数字。

# 四、区域 03：今日需要我处理

## 4.1 UI要回答的问题

这里不是“全部任务”，而是：

> Agent 无法自行安全完成、必须由用户审批、判断、补充信息或人工执行的任务。

首页要让用户知道：
- 什么事情；
- 为什么必须由我处理；
- 优先级；
- 截止时间；
- Agent建议；
- 证据/依据；
- 风险；
- 备注；
- 我能执行什么动作。

## 4.2 后台核心对象

```text
Task
TaskPlan
Approval
HumanActionRequest
Priority
FinalDecision
Policy
Permission
EvidenceRef
Deadline
TaskNote
```

建议新增系统级对象：
- `HumanActionRequest`
- `TaskNote`
- `EvidenceRef`

原因：不能把所有人工介入都模糊塞在普通 Task 文本里。

## 4.3 任务产生来源

```text
经营事件
  ↓
专业Agent分析
  ↓
Agent-1决策
  ↓
Task
  ↓
政策 / 权限判断
  ↓
┌──────────────┬──────────────┐
│ 可自动执行    │ 需人工介入    │
↓              ↓
Execution      HumanActionRequest
               ↓
          首页“需要我处理”
```

也允许以下来源直接产生人工任务：
- API权限不足；
- 平台动作无法自动化；
- 缺少业务信息；
- 高风险/不可逆动作；
- 法务/合规要求；
- 金额超过授权阈值；
- Agent判断置信度不足。

## 4.4 必须建立的任务状态机

至少应区分：

```text
created
queued
in_progress
waiting_human
waiting_external
approved
rejected
executing
validating
completed
cancelled
failed
expired
```

最终枚举后续单独定 Schema，但首页首先依赖 `waiting_human` / `requires_human=true`。

## 4.5 优先级不能只是 Agent 随口给 P0/P1

任务排序至少应考虑：
- 业务影响；
- 紧急程度；
- 延迟成本；
- 是否不可逆；
- 截止时间；
- 影响范围；
- 产品当前阶段；
- 是否阻塞其他任务。

Agent-1 现有动态优先级与目标冲突规则可以成为判断输入，但最终任务中心需要自己的统一 Priority Contract。

## 4.6 审批与执行边界

用户点击“批准”时不能直接等同于“业务成功”。

正确链路：

```text
批准
 ↓
ApprovalRecord
 ↓
Permission Check
 ↓
Execution
 ↓
ExecutionResult
 ↓
Validation
```

如果用户选择“拒绝”，必须记录：
- 谁拒绝；
- 时间；
- 原因/备注；
- 原 Decision 是否关闭；
- 是否允许 Agent 重新生成方案。

## 4.7 Agent / Skill职责

### Agent-1
- 判断是否需要人工介入；
- 汇总专业 Agent 建议；
- 决定最终任务优先级/冲突处理；
- 不能绕过系统权限直接执行。

### 专业Agent
- 提供领域分析和建议；
- 提供证据；
- 指明风险和可选方案。

### 系统任务中心
- 承载任务生命周期；
- 负责任务查询、状态、分配、排序、备注、截止时间和审批关系；
- 不是 Agent-1 的内部文件夹。

## 4.8 主要工程归属

```text
04_任务中心
05_执行系统
06_政策边界
02_Agent系统
03_技能系统
15_系统公共层/权限/日志
```

## 4.9 当前仓库覆盖判断

- Agent-1 内已有“任务调度”结构；
- Agent-1 已有决策、事件和任务编排相关能力；
- 执行层已有“人工审批/自动执行/回滚/结果回传”的框架；
- 但系统级独立任务中心、统一 Task 状态机、Approval Schema、HumanActionRequest：尚未正式建立。

这是首页落地的**一级核心缺口**。

## 4.10 首页MVP要求

先支持一种完整人工任务即可：

```text
广告异常
→ Agent建议调整预算
→ Agent-1生成任务
→ 因预算调整权限要求人工批准
→ 首页出现任务
→ 用户批准/拒绝
→ 记录审批结果
```

先闭环一类任务，比同时支持几十种任务更重要。

# 五、区域 04：Agent今日动态

## 5.1 UI要回答的问题

> 今天 Agent 团队真正做了什么？

这里不能展示模型 debug 日志，也不能把所有思考过程塞给用户。

只展示“对经营有意义、可追溯的业务活动”。

例如：
- 发现一个异常；
- 创建一个事件；
- 更新一个事件；
- 提交一个建议；
- Agent-1作出一个决策；
- 创建一个任务；
- 执行一个操作；
- 验证一个结果；
- 更新产品状态；
- 写入一条重要记忆。

## 5.2 后台核心对象

```text
Agent
AgentActivity
Event
DecisionItem
FinalDecision
Task
Action
ExecutionResult
ValidationResult
MemoryRef
ProductRef
```

`AgentActivity` 是这次反向拆解识别出的重要新增核心对象。

它与普通系统 Log 不同：
- Log = 给工程师排错；
- AgentActivity = 给业务用户理解 Agent 做了什么。

## 5.3 AgentActivity 最低字段

```text
activity_id
agent_id
activity_type
occurred_at
product_id / asin / sku
summary
business_reason
source_event_id
source_decision_id
source_task_id
source_action_id
result_status
importance
visibility
```

其中引用字段允许为空，但只要存在关联对象就必须带引用。

## 5.4 动态生成原则

不能让 Agent 自己写一段自然语言然后就算“活动记录”。

应该由系统在关键对象状态变化时生成结构化 Activity：

```text
Event created
→ Activity: “Agent-4发现广告异常”

FinalDecision created
→ Activity: “Agent-1确认调整广告策略”

ExecutionResult success
→ Activity: “系统完成竞价调整”
```

自然语言摘要可以由模板或模型生成，但结构化事实必须先存在。

## 5.5 聚合与降噪

如果同一产品 5 分钟内产生 20 条内部事件，首页不能刷屏。

需要：
- importance 阈值；
- 同类活动聚合；
- exact duplicate 去重；
- 产品维度归组；
- 默认只显示重要业务活动；
- 点击后进入完整活动/事件/任务详情。

## 5.6 主要工程归属

```text
02_Agent系统
04_任务中心
05_执行系统
09_记忆系统
15_系统公共层/日志与审计
12_系统运行层
```

## 5.7 当前仓库覆盖判断

- Agent-1 已有事件、决策、任务等局部结构；
- 系统公共层已有日志规划；
- 但“业务可见 AgentActivity”尚无独立统一对象；
- 当前日志体系与 UI 业务动态之间缺一层正式转换。

这是首页的**一级核心缺口**。

## 5.8 首页MVP要求

第一版只记录 5 类活动：
1. 发现重要 Event；
2. Agent-1形成 FinalDecision；
3. 创建人工/自动 Task；
4. 完成 Action；
5. Validation 完成。

这五类足以让首页初步不再是 Agent 黑箱。

# 六、区域 05：产品经营状态与今日操作

## 6.1 UI要回答的问题

这是首页最核心、后台工程最重的区域。

对于每一款产品，至少要回答：
- 这是什么产品；
- 现在处于哪个经营阶段；
- 当前经营状态如何；
- 当前核心目标是什么；
- 今天做了哪些操作；
- 目前还有哪些任务在进行；
- 最近阶段总结是什么；
- 点击后如何进入完整产品状态卡。

## 6.2 后台核心对象

```text
Product
ProductIdentity
BusinessState
ProductStage
Goal
MetricSnapshot
Event
Task
Action
ExecutionResult
ValidationResult
Memory
StageSummary
AgentActivity
```

建议明确新增：
- `ProductIdentity`
- `ProductStage`
- `StageSummary`

`ProductStage` 可以最终作为 `BusinessState` 的子对象或独立对象，后续 Schema 设计再决定；但业务语义必须显式存在。

## 6.3 Product 必须成为全系统第一关联主键

系统不能只靠 ASIN 文本串联数据。

建议未来使用内部：

```text
product_id
seller_account_id
marketplace_id
asin
sku
parent_asin
variation_family_id
status
```

所有以下对象必须最终能回指 `product_id`：
- Metric；
- Event；
- Goal；
- Decision；
- Task；
- Action；
- Memory；
- CompetitorLink；
- CampaignLink。

这是首页能把“同一个产品的一切”聚合到一张状态卡的前提。

## 6.4 产品经营状态生产链

```text
产品主数据
   +
销售/广告/流量/库存/价格/评价/利润数据
   +
历史经营记录
   ↓
经营指标标准化
   ↓
BusinessState Engine
   ↓
专业Agent判断
   ↓
Agent-1目标与策略
   ↓
ProductStage + Goal + State
   ↓
首页产品摘要
```

注意：
- “阶段”不能靠 UI 人工写死；
- “状态”不能靠某个 Agent 每次随口总结；
- 必须有可解释的识别规则、证据和最后更新时间。

## 6.5 今日已执行操作生产链

这是此前已经确认必须一级可见的信息。

每项操作至少需要：

```text
Action
├── action_id
├── product_id
├── actor_type       Agent / Human / System
├── actor_id
├── action_type
├── target_object
├── before_value
├── after_value
├── executed_at
├── reason
├── source_decision_id
├── source_task_id
├── execution_result_id
└── validation_status
```

这样首页才能真实展示：

> 谁、几点、为什么、具体改了什么、结果是什么。

而不是只显示“今日完成5个任务”。

## 6.6 当前任务生产链

```text
Goal
 ↓
FinalDecision
 ↓
TaskPlan
 ↓
Task
 ↓
状态：执行 / 等待 / 观察 / 验证 / 审批 / 等待触发
 ↓
产品状态卡“当前任务”
```

“今日操作”和“当前任务”必须使用两个不同查询口径：
- 今日操作：按 `executed_at` 查询真实 Action；
- 当前任务：按 Task 未结束状态查询。

## 6.7 历史总结生产链

```text
历史 Metric
+ Event
+ Decision
+ Task
+ Action
+ Validation
+ LearningRecord
   ↓
Memory Timeline
   ↓
阶段边界识别
   ↓
StageSummary
   ↓
产品状态卡最近阶段总结
```

阶段总结不能覆盖原始历史。原始记录仍按追加方式保留，摘要只是索引层。

## 7.1 UI要回答的问题

> 现在有哪些值得我知道，但不一定需要我立刻操作的风险、异常、竞争变化和增长机会？

关键边界：
- 重点异常/机会 ≠ 人工任务；
- 异常可以由 Agent 自动处理或继续观察；
- 只有需要人工动作时才进入“今日需要我处理”。

## 7.2 后台核心对象

```text

OpportunitySignal
AnomalySignal
CompetitorChangeSignal
Assessment
BusinessState
Product
EvidenceRef
WatchState
```

建议未来将这些 Signal 统一收敛到 Event 类型体系，而不是建立四套互不兼容的对象。

```text

| risk

```

## 7.3 事件生产来源

```text
数据变化
 ↓
规则 / Baseline / Threshold / Trend Detector
 ↓

 ↓
专业 Agent 分析
 ↓
结构化 Event
 ↓
去重 / 合并 / 关联
 ↓
```

Agent-1 不需要处理所有事件。

只有：
- 跨域冲突；
- 高影响；
- 需要形成经营决策；
- 需要任务；
- 需要人工审批；

- 事件去重；
- 事件关联；
- 观察窗口；
- 自动关闭/恢复；
- 重要性排序。

## 7.5 Agent职责映射

- Agent-3：竞品变化；
- Agent-4：广告异常/机会；
- Agent-5：流量异常；

表示系统已经执行了动作，但经营结果仍需继续观察。

六个区域看起来不同，但真正落地时高度依赖同一套共享基础设施。

- 站点时区；
- business_date；
- 今日窗口；

- 数据生效时间；


```text

 ↓
decision_id
 ↓

 ↓

 ↓

 ↓

```

任何一个首页操作都应该尽量能沿链追溯。

## 8.5 Actor统一

所有行为必须知道“谁做的”：

```text
actor_type = agent | human | system
actor_id
```

否则“今日操作”和审计体系无法成立。

## 8.6 权限与政策

每个动作至少需要判断：
- 可读取；
- 可建议；
- 可创建任务；
- 可自动执行；
- 必须审批；
- 禁止执行。

## 8.7 业务日志与工程日志分离

```text
EngineeringLog
= 系统运行、错误、调用、性能、调试

BusinessActivity / AgentActivity
= 用户需要理解的业务活动

ActionLedger
= 已真实执行的业务动作
```

三者不能混成一个日志文件。

## 8.8 首页聚合层

UI 不应该直接分别调用几十个 Agent 和数据库。

建议未来存在：首页聚合服务。

```text
HomeCommandCenterAggregator
├── OperatingSnapshot
├── HumanTasks
├── AgentActivities
├── ProductStatusCards
└── ImportantEvents
```

左侧导航由 ModuleRegistry / Permission 单独提供。
