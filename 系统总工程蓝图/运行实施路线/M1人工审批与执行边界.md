# M1 人工审批与执行边界 V1

> 对应任务：RI-03
> 目标：在 M0 只读链稳定后，引入 Task、人工审批和受控执行，但保持生产写权限最小化。

## 1. M1前置条件

进入M1前必须：
- M0的 ProductIdentity、MetricSnapshot、BusinessState、Event、Aggregator 链可用；
- 至少达到 READ_MODEL_VERIFIED；
- 若使用真实 Amazon 数据，需达到对应 LIVE_DATA_VERIFIED；
- Task/Approval/HumanActionRequest/Action/ExecutionResult Contract 已静态通过；
- Policy/Permission 有明确的运行判定入口。

## 2. M1最小闭环

推荐只开放一个受控动作类型，例如：

```text
广告异常 Event
→ Agent-4建议
→ Agent-1 FinalDecision
→ Task
→ HumanActionRequest
→ Human Approval
→ Permission Check
→ Executor
→ Action
→ ExecutionResult
→ Validation
→ Memory / AgentActivity / UI
```

第一版不得同时开放多类高风险写操作。

## 3. 审批不是执行

审批必须单独形成 Approval 事实：
- approver_id；
- decision；
- approved_at/rejected_at；
- reason/note；
- scope；
- authority reference。

Approval 成功后仍必须重新进行 Permission/Policy 检查，避免审批后权限已变化。

## 4. Executor硬边界

Executor只有在以下条件同时满足时才能执行：
- Task 是可执行状态；
- Action 类型在 allowlist；
- 权限范围覆盖目标 product/account/marketplace；
- required_controls 已满足；
- 需要审批时有有效 Approval；
- 幂等键/防重放成立；
- 执行前状态已保存；
- 风险阈值未触发阻断。

否则必须 fail closed。

## 5. M1第一版禁止

- 自动创建并自动批准同一高风险 Task；
- 无审批链直接放大广告预算；
- 批量价格修改；
- 删除 Listing/广告结构；
- 财务支付；
- 账户权限变更；
- 绕过 Amazon 或内部权限规则；
- 把 API 200 当作经营效果成功。

## 6. 执行结果与验证

```text
Action
 ↓
ExecutionResult
 ↓
ValidationResult
```

ExecutionResult 回答“动作是否被平台接受/执行”。
ValidationResult 回答“经营结果是否达到目标”。

验证必须有 observation_window，并读取后续 MetricSnapshot。

## 7. 人工拒绝路径

拒绝必须：
- 保存 Approval(rejected)；
- Task进入 rejected/cancelled 或重新方案状态；
- AgentActivity 记录业务可见事件；
- 不自动重试同一方案；
- 如重新生成方案，必须生成新 Option/Decision 引用链。

## 8. M1验收门禁

- HUMAN_APPROVAL_VERIFIED：真实用户身份完成一次可追溯批准/拒绝。
- EXECUTION_VERIFIED：授权受控动作真实执行并产生 ExecutionResult。
- VALIDATION_VERIFIED：执行后完成独立业务验证。
- 只有完整对象链、机器证据和 UI 回写同时成立，才允许进入 BUSINESS_LOOP_VERIFIED 候选。

## 9. L1结论

M1 的人工审批、权限复核、Executor fail-closed、执行与验证边界已明确；未实施真实写权限。L1：PASS。
