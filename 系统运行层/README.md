# 系统运行层

本目录负责让各 Agent 真正被程序装载和运行，是整个智能体系统的“发动机舱”。

## 系统定位
Agent库负责定义“谁来思考、目标是什么、业务上应该怎么判断”；系统运行层负责解决“这些定义如何被程序读取、如何调用大模型、如何获得上下文、如何继续行动、如何留下运行记录”。

系统运行层本身不替代 Agent-1 至 Agent-13 的业务智能，也不应把业务知识全部搬到这里。

## 当前框架
- Agent运行器：装载 Agent 并控制一次完整运行。
- 大模型运行时：统一调用大模型、组装提示词和接收结构化输出。
- 上下文管理：为本次运行选择和组织必要上下文。
- 工具调用管理：连接 Agent 与共享工具层。
- 会话与运行记录：保存每次实际运行过程。
- 异常与保护：处理超时、循环失控、工具失败和信息不足。
- 配置：保存系统运行参数和开关。
- 测试：定义系统运行层的最小验收闭环。

## V0.1最小闭环
手动输入事件 → 指定 Agent-1 → 装载 Agent-1 → 构建上下文 → 组装模型输入 → 调用大模型 → 解析结构化结果 → 保存运行记录。

## 关于施工顺序
当前建议顺序保留为工程意见，而不是硬性约束：

Agent装载器 → 大模型运行时 → 提示词组装器 → 上下文管理 → 结构化输出 → 运行记录 → 自主循环 → 工具调用。

实际施工前必须检查目标 Agent 的业务内容是否足够成熟。如果 Agent-1 只有目录和框架、缺少可执行的目标、知识、判断标准、技能内容和案例，那么即使运行层已经写完，也只会得到一个“能调用模型但业务能力空心”的 Agent。

因此当前项目采用“双线建设”：
1. 系统运行层先建立统一框架和最小运行能力。
2. Agent-1 同步从“框架”进入“业务内容与技能实现”，达到可运行最低标准后再正式接入运行器。

## 当前状态
系统运行层：框架建设阶段。
Agent-1：已有工程结构和部分规则设计，但业务知识、技能实现、真实工具与数据能力仍需继续填充。

## 核心原则
- Agent 负责岗位智能与决策逻辑。
- 系统运行层负责把静态定义变成可执行过程。
- 所有 Agent 共用统一运行时，避免重复建设。
- 不用运行层弥补 Agent 本体内容不足。
- 不为了“能跑”而牺牲业务判断质量。
